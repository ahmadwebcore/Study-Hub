# StudyHub — Application Security & Row Level Security (RLS) Architecture

This document outlines the security architecture, threat model, access control policies, and database safeguards implemented in **StudyHub**.

---

## 1. Security Philosophy & Threat Model

StudyHub follows a **Zero-Trust, Defense-in-Depth** architecture. 

### Fundamental Security Tenet
> [!IMPORTANT]
> Frontend route guards (e.g. React Router `<ProtectedRoute />`) and UI role toggles are purely **User Experience conveniences**. They do NOT constitute an access control boundary. 
> 
> **True security is enforced strictly at the database layer** via PostgreSQL Row Level Security (RLS), database triggers, and storage access policies. Any direct REST, GraphQL, or RPC API call executed against Supabase is subject to the exact same database-level checks.

### Threat Scenarios Mitigated

| Threat | Vector | Mitigation Strategy |
|---|---|---|
| **Privilege Escalation** | Student edits profile payload to set `role: "teacher"`. | PostgreSQL trigger `protect_role_escalation` throws an exception if a non-teacher attempts to modify the `role` column. |
| **Data Leakage Across Students** | Student alters UUID in request to read another student's homework submission. | RLS policy on `submissions` ensures students can only `SELECT` records where `student_id = auth.uid()`. |
| **Unauthorized Grade Modification** | Student updates submission score or feedback. | RLS policy allows only users where `is_teacher() = true` to `UPDATE` submissions. |
| **Unauthorized Storage Access** | Direct access to uploaded exams or student assignment PDFs. | Storage buckets are completely private (`public = false`). Storage RLS permits access only via signed time-limited tokens (TTL: 3600s) generated by authorized sessions. |
| **Unrestricted Account Creation** | Bad actor registers as an administrator or arbitrary student. | Public registration is disabled for students. Onboarding requires a cryptographically secure invitation token generated exclusively by an authorized faculty member. |

## 2. Row Level Security (RLS) Policy Matrix

RLS is enabled on **100% of exposed database tables**.

```sql
ALTER TABLE public.profiles ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.invitations ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.subjects ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.syllabus_units ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.syllabus_topics ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.study_schedules ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.assignments ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.submissions ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.tests ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.results ENABLE ROW LEVEL SECURITY;
```

### Detailed RLS Matrix

| Table | Operation | Role | Policy Condition |
|---|---|---|---|
| **profiles** | `SELECT` | Authenticated | Can view any profile within the academic cohort |
| | `UPDATE` | Self | `id = auth.uid()` (Cannot update `role` unless teacher) |
| **invitations** | `SELECT` | Teacher / Anon with token | Teachers see all; Invitees can lookup by token during signup |
| | `INSERT` / `UPDATE` | Teacher | Only users where `is_teacher() = true` |
| **subjects** | `SELECT` | Authenticated | All enrolled users can read curriculum subjects |
| | `ALL` | Teacher | Only teachers can create, update, or delete subjects |
| **syllabus_units** | `SELECT` | Authenticated | All users can view syllabus units |
| | `ALL` | Teacher | Only teachers can edit curriculum units |
| **syllabus_topics** | `SELECT` | Authenticated | All users can view topics |
| | `UPDATE` | Authenticated | Students can toggle topic `completed` checkpoints |
| | `INSERT` / `DELETE` | Teacher | Only teachers can modify structure |
| **study_schedules**| `SELECT` | Authenticated | Students view own schedule; Teachers view cohort schedules |
| | `ALL` | Teacher | Teachers manage timetable entries |
| **assignments** | `SELECT` | Authenticated | All users can view assigned homework |
| | `ALL` | Teacher | Only teachers can author or edit assignments |
| **submissions** | `SELECT` | Student | `student_id = auth.uid()` (Own submissions only) |
| | `SELECT` | Teacher | Can inspect all submissions across the cohort |
| | `INSERT` | Student | `student_id = auth.uid()` (Submit own solution) |
| | `UPDATE` | Teacher | Only teachers can grade and enter feedback |
| **tests** | `SELECT` | Authenticated | All users can view scheduled tests |
| | `ALL` | Teacher | Only teachers can schedule or alter exams |
| **results** | `SELECT` | Student | `student_id = auth.uid()` (Own results only) |
| | `SELECT` | Teacher | Can view cohort grade distribution |
| | `ALL` | Teacher | Only teachers can publish marks |

## 3. Defense Against Infinite RLS Recursion

In naive Supabase RLS implementations, querying `profiles.role` inside a `profiles` RLS policy causes an infinite recursive loop:
```
policy -> SELECT profiles -> policy -> SELECT profiles -> ... (Server Crash)
```

StudyHub resolves this using a **Security Definer** helper function marked as `STABLE`:

```sql
CREATE OR REPLACE FUNCTION public.get_auth_role()
RETURNS public.user_role AS $$
  SELECT role FROM public.profiles WHERE id = auth.uid();
$$ LANGUAGE sql STABLE SECURITY DEFINER;

CREATE OR REPLACE FUNCTION public.is_teacher()
RETURNS BOOLEAN AS $$
  SELECT public.get_auth_role() = 'teacher';
$$ LANGUAGE sql STABLE SECURITY DEFINER;
```

Because `get_auth_role()` runs with security definer rights and queries the primary key directly, PostgreSQL bypasses the RLS stack for that single lookup, delivering instantaneous, recursion-free authorization.

## 4. Role Escalation Protection

A dedicated PostgreSQL trigger prevents privilege escalation:

```sql
CREATE OR REPLACE FUNCTION public.protect_role_escalation()
RETURNS TRIGGER AS $$
BEGIN
  IF NEW.role <> OLD.role AND NOT public.is_teacher() THEN
    RAISE EXCEPTION 'Unauthorized: Only faculty administrators can elevate user roles.';
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER tr_protect_role_escalation
  BEFORE UPDATE ON public.profiles
  FOR EACH ROW
  EXECUTE FUNCTION public.protect_role_escalation();
```

Even if a malicious user crafts a direct `curl` request:
```bash
curl -X PATCH 'https://...supabase.co/rest/v1/profiles?id=eq.<user_id>' \
  -H "Authorization: Bearer <student_jwt>" \
  -d '{"role":"teacher"}'
```
PostgreSQL intercepts the update and aborts the transaction with an exception.

## 5. Storage Security & Time-Limited Signed URLs

StudyHub provisions two dedicated private storage buckets:
- `student-submissions`: Maximum file size 25MB (PDF, DOCX, ZIP).
- `syllabus-materials`: Maximum file size 50MB (PDF, PPTX).

### Storage RLS Policies
Files stored in `student-submissions` are organized by student folder:
```
student-submissions/
└── <student_uuid>/
    └── <assignment_id>_<timestamp>.pdf
```

Storage policies enforced on `storage.objects`:
1. **Uploads**: Only authenticated students can upload into their own folder:
   ```sql
   (bucket_id = 'student-submissions' AND (storage.foldername(name))[1] = auth.uid()::text)
   ```
2. **Downloads**: Only the owner student or a verified teacher can download:
   ```sql
   (bucket_id = 'student-submissions' AND ((storage.foldername(name))[1] = auth.uid()::text OR public.is_teacher()))
   ```
3. **Signed Download Pattern**: All client downloads use signed URLs generated with a 60-minute expiration window (`storageService.createSignedDownloadUrl`). No direct public URLs are ever exposed.

## 6. Authentication System & Credentials

- **GoTrue Auth**: Passwords are encrypted using bcrypt or Argon2 by the Supabase GoTrue service. StudyHub never stores or handles raw plaintext passwords.
- **Session Tokens**: JWT access tokens have a short lifespan (1 hour) and are automatically refreshed using secure refresh tokens stored in `localStorage` under Supabase client domain isolation.
- **Service-Role Key Protection**: The Supabase `service_role` key has full administrative bypass permissions. It is **never** bundled or referenced anywhere in frontend code. Only `VITE_SUPABASE_ANON_KEY` is utilized.

## 7. Prepared Security Scaffolding

### Google OAuth Integration
Prepared in `src/services/authService.ts` via PKCE (Proof Key for Code Exchange) flow:
```typescript
await authService.signInWithGoogle();
```
Requires setting Google Client ID & Secret in Supabase Auth Providers before production activation.

### TOTP Multi-Factor Authentication (MFA)
Supabase Auth supports standard RFC 6238 TOTP (Google Authenticator, 1Password, Authy). The database schema and profile architecture are ready for MFA challenge enrollment in a future security milestone.
